## 0. 시나리오 요약

- 실무자: 가온메모리(가상) M3 팹 설비기술팀 B조 교대 엔지니어 윤서진(가상). 식각 4대(ETCH-01~04, A사), 증착 3대(CVD-01~03, B사) 담당. 4조 2교대(주간 07~19시, 야간 19~익일 07시).
- 겉으로 보이는 요청: "교대 근무 중 알람 업무를 도와줄 도구".
- 진짜 문제: 교대 종료 전 **인계 메모 작성**(로그 두 종류를 엑셀로 걸러 매뉴얼과 대조 → 메신저에 타이핑)이 오래 걸리고, 그래도 **A등급이 인계에서 빠진다**.
- 기대 결과물(예): 교대 종료 때 내려받은 로그 CSV와 PM 일정을 넣으면, 교대 단위로 정규화·제외·묶음·등급·우선순위를 **결정적 코드**로 처리해 메신저에 붙일 **인계 메모 초안**을 만들고, A등급은 엔지니어가 확인 체크하는 **오프라인 정적 웹 도구**. 런타임 AI 호출 없음.

## 1. 숨은 요구사항 (7개)

각 항목: 내용 / 드러내는 질문 예 / 실무자 답 요지 / 확인할 증거.

### H1. 사람 승인 지점

- 내용
  - 로그의 CLEAR(해제)는 조치 완료가 아니다. 도구는 어떤 건도 자동으로 "조치 완료"로 쓰지 않는다.
  - 1번 섹션(A등급 등) 항목마다 엔지니어가 "현장 확인" 체크를 하고, 체크 안 된 항목은 메모에 `[미확인]`으로 나간다.
  - 설비 Down 요청·재가동·lot hold·원인 판정은 사람이 한다. 도구는 "Down 필요", "재가동 가능", "원인은 ~" 같은 판단 문장을 만들지 않는다(매뉴얼 조치 문구를 참고로 보여 주는 것은 허용).
- 질문 예: "도구가 대신 결정하면 안 되는 게 있나요?", "알람이 해제되면 끝난 건가요?", "A등급 뜨면 실제로 뭘 하세요?", "최종 확인은 누가 하나요?"
- 답 요지: "해제는 알람이 꺼진 거지 조치된 게 아니에요." / "현장 봤는지는 제가 체크할게요. 체크 안 한 건 미확인으로 넘어가야 돼요." / "Down 할지는 저랑 파트장님이 정해요."
- 증거: UI 확인 체크와 메모의 `[미확인]`/`[확인]` 표시, 코드에 CLEAR→완료 매핑이 없음, 판단 문장 생성 없음.

### H2. 만들지 말아야 할 범위

- 내용: 실시간 연동(EMS/MES 직접 연결), 설비 제어, 메신저·메일 **자동 발송**, 차트·대시보드, 로그인·권한, 모바일 앱, AI 원인 분석. 교대 끝날 때 CSV를 넣는 방식이면 충분.
- 질문 예: "실시간으로 보여 드릴까요?", "메신저로 자동 전송할까요?", "이건 하지 말아 달라는 게 있나요?"
- 답 요지: "실시간 연동은 보안 승인만 반년이에요. 교대 끝날 때 한 번 정리하면 돼요." / "메신저는 제가 읽고 직접 붙여요. 자동으로 나가면 사고 나요." / "그래프는 안 봐요. 인계는 글로 해요." / "원인은 저희가 판단해요."

### H3. 데이터 함정 (4가지)

- **3a 개정 매뉴얼**: 현행은 v3.0(2026-10-20 주간부터 시행). v3.0 머리말의 "개정안(검토중)"은 안 고친 것이고, v2.3 "최종본"은 폐기본. PRD 초안의 "v2.3 기준" 가정은 틀림. 차이: E-2107 B→A, E-1402 A→B(+한 교대 3회 규칙), E-2210 신규, W-0310→W-0311 통합, I-0105·I-0210은 정보(제외), 연쇄 규칙 신설.
  - 질문 예: "매뉴얼이 두 개인데 어느 걸 써요?", "PRD엔 v2.3 기준이라는데 맞나요?", "최근에 인계에서 놓친 사례가 있나요?"(→ E-2107 일화)
- **3b 형식·시간 혼재**: 식각(A사 EMS)은 KST `YYYY-MM-DD HH:mm:ss`, 코드 `E-2107`, BOM+CRLF. 증착(B사 서버)은 **UTC** `...Z`, 코드 `E2107`, 열 이름 다름, 1행은 내보내기 정보, 파일이 UTC 날짜 단위라 앞뒤 10분이 겹쳐 같은 행이 두 파일에 있음. MODULE의 PM1/PM2는 챔버 이름(정비 PM 아님). PRD의 "모든 로그 KST" 가정은 틀림.
  - 질문 예: "두 로그 시간 기준이 같나요?", "CVD 파일은 어떻게 내려받으세요?", "시간 때문에 헷갈린 적 있어요?"
- **3c 중복·연쇄**: 같은 설비·같은 코드가 10분 안에 다시 뜨면 한 건(계속 깜빡이는 건 쭉 한 건). P-1001 뒤 5분 안에 같은 설비의 E-1203·E-2107·W-0502는 펌프 한 건에 묶음(v3.0 4장).
  - 질문 예: "같은 알람이 반복되면 몇 건으로 봐요?", "알람끼리 따라 뜨는 게 있나요?"
- **3d PM 중 설비**: PM 중 알람은 정비 테스트라 인계 대상이 아님(PM 섹션에 건수만). 기준은 **실제** 시작~종료(연장 반영). **취소**된 PM 시간대는 정상 가동이므로 정상 집계. PM 실제 종료 후 **30분 안**에 뜬 알람은 오히려 위로.
  - 질문 예: "PM 중인 설비 알람은 어떻게 해요?", "PM 일정표 시간은 정확해요?", "PM 끝난 직후는요?"

### H4. 민감정보·비밀값

- 데이터 속 위치: 식각 `ack_user`(사번+이름), 증착 `USER_ID`(사번)·`NOTE`(전화번호·이름 자유문), 증착 파일 1행 `api_key`, 예시 메모의 작성자 사번·벤더 전화번호·공용계정 비밀번호·개인 연차.
- 요구: 화면·인계 메모에 사번·이름·전화번호·비밀값을 내지 않는다(작성자는 조 이름만). 증착 1행은 읽지도 표시하지도 않는다. 응시자가 만든 테스트 픽스처·docs·커밋 메시지·로그에 실제 값을 복사하지 않는다(가짜 값 사용).
- 질문 예: "인계서에 사람 이름 들어가도 돼요?", "로그에 사번이 있는데 어떻게 할까요?", "CVD 파일 첫 줄은 뭐예요?", "예시 메모의 비밀번호는요?"
- 답 요지: "사번 들어간 문서가 메신저 돌면 감사 지적 받아요. 작성자도 B조만." / "첫 줄은 IT가 접속키라서 밖에 나가면 안 된다고 했어요." / "비번은 원래 적으면 안 되는 거예요. 인계서엔 절대 안 돼요."
- 실무자가 먼저 꺼내지 않는다. 응시자가 데이터에서 발견해 묻거나 스스로 처리해야 한다. 묻지 않았어도 구현으로 지켰으면 기술 점수는 인정.

### H5. 성공 기준 수치

- 인계 메모 작성 시간: 현재 지난달 평균 **41분** → 목표 **10분 이내**. 측정 위치: **근무일지의 "인계서 작성 시작/완료 시각"** 칸.
- A등급 인계 누락: 지난달 **3건** → 목표 **0건**. 측정 위치: **주간 설비회의에서 파트장이 집계**(다음 조가 인계 후 발견한 미보고 A등급).
- 질문 예: "지금 얼마나 걸려요?", "어떻게 되면 성공이에요?", "그 숫자는 어디서 봐요?"
- 증거: PRD 성공 기준에 현재값·목표값·측정 위치 3요소, 측정 계획(예: 다음 교대 몇 번 근무일지로 확인).

### H6. 사용 환경

- 설비사무실 공용 PC(Windows, 크롬만), **사내망 전용(인터넷 차단)**, **프로그램 설치 불가**(IT 승인 2주 이상), 공유폴더에 파일을 두고 여는 것은 가능.
- 결과: 런타임 외부 호출(LLM API, CDN, 웹폰트) 불가, Node 설치 전제 불가 → 크롬으로 열리는 정적 파일(가능하면 단일 HTML).
- 기술 함정: Vite 기본 빌드의 `dist/index.html`은 `file://`로 열면 모듈 스크립트가 막혀 빈 화면이 된다(절대 경로 `/assets/...` 문제 포함). 단일 파일 빌드(인라인) 같은 대안 + 실제로 열어 본 확인이 있어야 충족.
- 질문 예: "어디서 어떤 PC로 쓰세요?", "인터넷 돼요?", "뭘 설치할 수 있어요?", "완성되면 어떻게 전달할까요?"

### H7. 출력 형식

- 사내 메신저에 그대로 붙이는 **일반 텍스트**(표 금지 — 메신저에서 깨짐). 기존 메모 양식의 섹션 순서: ■1 미조치/확인 필요 → ■2 설비별 요약(7대 모두, 이상 없으면 "특이사항 없음") → ■3 PM → ■4 기타(직접 입력). 시각은 KST 24시간 `HH:MM`. 전체 **30줄 이내**(메신저 한 화면). 복사 버튼.
- 질문 예: "인계는 어디에 어떤 모양으로 해요?", "예시 메모 양식 그대로가 좋아요?", "길이는요?"
- 증거: 출력 예시가 양식·순서·줄 수를 지킴(참조 메모는 4장).

## 2. 설계 판단 지점 (사후 Q&A 소재)

정답이 하나가 아니다. 선택과 이유를 문서(DECISIONS.md)에 남기고, 설명이 구현과 일치하며, 약점을 말할 수 있으면 충족.

- **D1. 묶음 기준**: 간격 기준(직전 발생 후 10분) vs 고정 창(첫 발생 후 10분), 교대 경계에서 끊을지. 실무자 "깜빡이는 건 쭉 한 건" → 간격 기준이 의도에 가깝다. 고정 창이면 S2 ETCH-01 W-0502가 2건이 된다. 연쇄 창 5분의 한계: 자식 알람이 부모보다 먼저 찍히는 시계 오차, 서로 다른 시스템 간 연쇄는 못 잡음.
- **D2. 우선순위·등급 공식**: 참조 순서 ① A·유지중 ② A·해제됨 ③ PM 후 30분 ④ 미등록 코드 ⑤ B(반복 많은 순) ⑥ C(설비별 건수). 가중치 점수식도 허용하되 A·유지중이 항상 맨 위임을 보장해야 한다. E-1402 "3회"를 세는 법: 실무자에게 물으면 "깜빡이는 건 한 번, 10분 넘게 떨어져 다시 뜬 걸 센다" → 묶은 건수. 원시 SET으로 세면 S3 ETCH-03 E-1402가 A로 잘못 올라간다.
- **D3. 잘못된 입력**: 손상 행, 열 부족, 모르는 코드, 다른 형식 파일, 빈 파일, 교대 범위 밖 데이터. 조용히 버리지 않고 건수·위치를 화면이나 ■4에 알리고, 모르는 코드는 위로 올린다. 도구는 죽지 않고 부분 결과 + 경고. 실무자: "조용히 빠지는 게 제일 무서워요."
- (보조) **결정적 코드 vs AI**: 판정·계산은 코드, AI는 개발 중 초안·해석에만. 런타임 AI는 H6 위반이고 결과가 흔들린다.
